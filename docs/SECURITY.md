# Security and recovery boundaries

This is an initial implementation with automated unit tests and an isolated TensorCash Core [regtest signing gate](../scripts/signing-gate.ts). It has not received an independent security audit or a public mainnet spending trial. Passing these checks does not establish that a browser wallet is safe for substantial funds. Generate current test reports locally; historical operational evidence is excluded from the source repository. Mainnet verification uses read-only public data.

## What the wallet protects

Private HD keys are generated and used inside a dedicated Worker. The wallet creates a 12-word English BIP39 mnemonic from browser cryptographic randomness, using an empty BIP39 passphrase. The phrase is deliberately returned to the local UI for backup and for an explicitly authenticated reveal; it is never sent to the gateway. Before a new wallet can sign, the user must confirm its backup. Restore also validates the mnemonic checksum.

The entropy boundary is `newMnemonic()` → `@scure/bip39.generateMnemonic(englishWordlist, 128)` → `@noble/hashes.randomBytes(16)` → `globalThis.crypto.getRandomValues`. There is no fallback to `Math.random`, timestamps, passwords or device identifiers. Missing or throwing cryptographic randomness aborts creation before storage or an unlocked session. The canonical English list contains all 2048 distinct words, with no selection filter. The 12 words encode 128 entropy bits plus four SHA-256 checksum bits; checksum bits do not add entropy. Every word enters BIP39 PBKDF2-HMAC-SHA512 (2048 rounds), and its complete 64-byte result enters BIP32 master derivation. That expansion does not increase the original entropy. See the [BIP39 specification](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki).

A cryptographic pseudorandom generator is the intended source, as described by [Web Crypto](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/#Crypto-method-getRandomValues). Security assumes a correctly implemented, uncompromised browser and operating system with sufficient entropy. An API that silently returns predictable bytes cannot be certified by application-level sample or duplicate checks. With independent, uniformly distributed 128-bit entropy, two generated phrases match with probability `2^-128`; among one billion phrases, the birthday collision probability is approximately `1.47e-21`. This is a conditional probability, not a guarantee of globally unique phrases. Repeated words inside one valid phrase are allowed.

Regression checks in [entropy.test.ts](../tests/unit/entropy.test.ts) pin the requested random-byte length, the canonical wordlist file hash, all 2048 reachable first-word indices, official public BIP39/BIP32 vectors, complete 64-byte seed delivery compared with an independent PBKDF2 implementation, preservation of each entropy bit, and failure before storage/session activation when the RNG is missing or throws. These are deterministic implementation checks, not a measurement of browser entropy or an independent security audit.

The IndexedDB vault contains encrypted secrets and public wallet metadata. Its versioned format uses scrypt, a random 16-byte salt and AES-256-GCM with a fresh 12-byte IV and a 128-bit authentication tag. Public metadata, network, derivation, KDF parameters, salt and IV are authenticated. The seed must reproduce the declared account xpub and fingerprint. Public metadata accepts an account xpub, never an xpriv.

The default scrypt cost is `N=131072`, `r=8`, `p=1`, with a 32-byte derived key. Imported vaults accept only power-of-two `N` between 32768 and 262144, the same `r/p/key length`, and bounded input sizes. Passwords contain 12–256 characters. These are resource and format bounds; a predictable password remains vulnerable to offline guessing. AES keys are non-exportable WebCrypto keys in memory. Password changes generate a new salt and IV. Older exported backups continue to require their original passwords.

Storage updates compare the prior ciphertext atomically to prevent concurrent tabs from overwriting a changed wallet. Unlocked metadata and receive-address discovery use the authenticated session and reject a replaced stored vault, as does signing. Public discovery and background refresh do not extend the signing session lifetime. Actual pointer/key activity and return to a visible wallet renew the five-minute idle deadline only if it has not expired. The Worker independently enforces that deadline before allowing activity or signing, including when browser timers were suspended. Switching tabs preserves an unexpired session while obscuring a displayed recovery phrase. UI locking terminates the Worker and discards private state. Locking does not revoke a signature already released for publication.

Balance display and permission to send are separate. The UI keeps the last complete balance and history during refresh or provider failure, and shows an unknown value before the first complete read. A stale or incomplete view pauses new sending; it is not a zero-balance observation. The total native balance includes both eligible outputs and verified outputs awaiting confirmations. Previously known amounts remain visible while freshness is being checked.

A separate bounded IndexedDB display cache preserves the last verified balance, recent activity and owned receive addresses across locking and page reloads. It is encrypted with the unlocked non-exportable vault key, a fresh AES-GCM IV and separate authenticated context bound to the wallet identity, network, public account and vault salt. It is decrypted only after unlocking, atomically rekeyed on password change, and removed when the wallet is removed or replaced. Seed backup files retain their original format and do not include this optional cache. Corruption or a storage failure cannot prevent unlocking or a successful network refresh.

Cached values are explicitly labelled last known with the original verification time. Cached snapshots contain no UTXOs, parent raw transactions or spend graph, and carry `ready: false` and `complete: false`; they cannot supply inputs or authorize sending. Discovery starts afresh after unlock. Cached activity is capped at 200 entries and labelled recent when truncated. Cache reads and writes do not extend the signing session deadline. An unresolved publication journal or accepted transfer projection suppresses cache restoration to avoid restoring a prepayment balance.

## Transaction controls

This release sends ordinary native TSC using P2WPKH inputs and recipients (`tc1q…` on mainnet, `bcrt1q…` on the isolated ordinary regtest profile). It does not support assets, ICU, rotation transactions, Taproot spending, legacy recipients or Tensor-specific extensions. A native TSC output inside an extension-bearing parent transaction is also excluded. Missing parent raw data makes an output unspendable through this wallet.

The signer independently decodes the entire parent raw transaction, requires canonical lengths, rejects unknown flags/versions and trailing data, and computes its txid locally. Parent identity, output index, amount, script and owned derivation must agree. A provider's `native` or `verified` label alone is insufficient. Core independently classifies parents and checks current UTXOs, confirmations, coinbase maturity and mempool acceptance before publication.

P2WPKH signatures use `SIGHASH_ALL` and the pinned scure/noble secp256k1 implementation. Its ECDSA nonce is derived deterministically from the private key and transaction digest using [RFC6979](https://www.rfc-editor.org/rfc/rfc6979), rather than newly sampled for each signature. This does not compensate for a predictable original seed. There is no separate browser-side ECDSA signature verification after finalization; Core's `testmempoolaccept` verifies acceptance before publication. JavaScript execution does not provide a general guarantee against timing or memory side channels.

Amounts and fees use integer base units (`100000000` units per TSC). Inputs are deduplicated; recipient and internal change scripts are checked, and change is independently derived again before signing. The reviewed amount, fee and outputs are fixed. Plans expire after two minutes and Worker plans are single-use. Selection is bounded to 100 inputs; the signer enforces an absolute fee cap of 1000000 units, a 5% input-value fee cap, bounded rates, conservative dust thresholds and the requested floor against the final signed vsize. The gateway additionally applies its configured fee caps and the live relay/mempool floor.

A broadcast timeout is an unknown outcome, not proof that a payment failed. Before contacting the validation or broadcast endpoint, the UI persists a public retry journal containing the reviewed plan and identical signed raw transaction. It verifies and restores this record after lock/reload and blocks new payments and local wallet removal until the transfer is resolved. The journal contains no seed, password, private key or PSBT, but reveals transaction details and can be lost through browser storage clearing. Retry uses the same raw transaction and txid; intentionally creating another payment after losing this record can cause a duplicate payment.

The journal records a broadcast attempt before making that request. A definitive validation rejection clears a transfer automatically only when no publication was attempted. After an attempt, explicit cancellation is offered only when the gateway proves current rejection, absence from its Core mempool and every input still unspent against consistent chain and mempool observations; the UI repeats this check immediately before discarding the record. Unavailable inputs, uncertain outcomes, changes during the check and RPC failures retain the record. This establishes current state, not revocation of the released signature: a retained raw transaction or delayed external submission may become acceptable later if chain state or policy changes.

After a matching accepted/already-known response, a separate bounded public receipt cache retains the signed transaction and reviewed plan across reloads. It immediately removes consumed inputs from the displayed balance and adds owned recipient/change outputs with zero confirmations. Such locally projected outputs never obtain inferred confirmations or permission to spend. Receipts remain until a complete provider view corroborates the transaction and its owned outputs or verified subsequent spends. Unresolved local projections pause new sending. An unknown broadcast outcome stays in the blocking retry journal, rather than being represented as accepted. Both stores contain public transaction details and can be lost by clearing browser storage.

Core confirmation through a pinned active-chain block, mempool presence or a matching current output can establish that the identical transaction is already known. If a confirmed transaction's block is pruned and all of its outputs have been spent, the gateway may be unable to prove its status and fails closed. An archival source or independent reconciliation is then required. Release verification must include timeout followed by lock/reload and retry.

## Recovery and address limits

The wallet's version 1 scheme is exactly `m/84'/1'/0'`, with receive branch `/0/index` and change branch `/1/index`, on both supported networks. This follows the inspected TensorCash Core descriptor convention, including its non-Bitcoin mainnet coin-type behavior. It is a declared wallet scheme, not a promise that an arbitrary TensorCash wallet will discover the same mnemonic. No additional BIP39 passphrase is supported; a wallet created elsewhere with one will not restore correctly here. Core `wallet.dat` files are not mnemonic backups and cannot be imported.

Discovery checks both branches with a gap of 20 unused addresses and scans at most 200 addresses per branch. The supported issuance range is 180 addresses per branch, indices `0..179`; the remaining 20 positions provide the trailing recovery gap. At index 179 the wallet reuses the terminal address and displays a range warning. The UI also bounds issuance of unused receive addresses to preserve the gap. Activity after index 179, beyond a gap of 20, in accounts other than zero, or under different derivation paths requires a tool with explicit extended recovery support. Hitting an incomplete-history or scan limit fails closed; it must not be interpreted as a zero balance. A saved public receive cursor is a convenience, not a substitute for the phrase and declared derivation scheme.

Keep an offline mnemonic backup, or an encrypted backup plus its password, outside browser storage. Browser eviction, private browsing, storage clearing, OS failure or loss of the device can remove the local vault. Restoring a phrase does not recreate deleted archival blockchain data: complete history and spend verification still require a provider retaining the relevant raw transactions.

## What remains trusted

The provider sees queried public addresses and can correlate them, hide activity, return incomplete history or refuse service. The account xpub is public metadata in the local backup and exposes watch-only address discovery to anyone who obtains it. Genesis and observation-freshness checks catch configuration mistakes; they are not independent consensus, SPV or proof-of-inclusion verification. The wallet adds no block-age-only cutoff for balances or publication: a freshly checked, complete index at the accepted Core tip remains usable during a mining pause. Core/provider initial-download and work-readiness checks still apply; a restart during a long gap can re-enter IBD, which this fix does not bypass. Only the known explorer block-age/pending-header advisories are tolerated with exact tip alignment, fresh status and full effective-work verification. Stale observations, unknown warnings, incomplete history and unavailable providers still fail closed. Removing a mining-age cutoff does not prove peer connectivity, independent chain visibility or protection against an eclipse; a consistent but isolated node/provider can still miss global activity. Browser-side transaction checks prevent many malformed or substituted signing requests, but cannot prove that the provider disclosed every coin or transaction.

An accepted-tip view excludes blocks whose headers are still awaiting validation. There is no separate limit on that header backlog's size or duration. If an external validator stalls, an internally consistent accepted-tip/index view can remain usable while missing activity from those unaccepted blocks; later acceptance can invalidate a mempool transaction. A stricter pending-validation policy is separate from a mining-age cutoff and requires an explicit operator decision.

Mainnet pending activity is reconciled directly with the gateway's current Core mempool, independently of pending address-index rows. The gateway checks relevant ordinary transaction bytes, prevouts and current outputs, and returns an active spend graph. Membership and tip checkpoints are checked again before a complete snapshot is returned. Immutable transaction caches do not cache balances or mempool membership. Limits or missing verification make the view incomplete; they must never become a complete empty balance. Visibility begins when this Core node observes a transaction, not necessarily when another node first receives it. Confirmed address history still requires the external index and relevant archival raw data.

The gateway holds Core RPC credentials on the server. These credentials retain the capabilities of that RPC endpoint even though the wallet API exposes only an allowlisted set of operations. Keep the gateway and its node isolated from funded bridge wallets, restrict filesystem and network access, and keep credentials out of the browser build, request logs and backups. Production HTTPS and a controlled application origin are necessary. The production server sets CSP, frame restrictions, no-referrer and no-store for wallet API data; assets are bundled locally without analytics or remote scripts.

Ordinary Core cookie files must have no group/other access (0400 or 0600). A narrow exception supports systemd's read-only service ACL: a root-owned 0440 file is accepted only at the exact `${CREDENTIALS_DIRECTORY}/core.cookie` under `/run/credentials/`, inside a root-owned directory with no access for others and no group writes. Both paths must resolve without symlink substitution. Group-readable source cookies, other filenames and arbitrary credential directories remain rejected. This lets an unprivileged service read its `LoadCredential` copy without changing the original Core cookie permissions or exposing credentials in logs.

A Worker is a lifecycle boundary, not a defense against malicious code from the same origin. A compromised host, substituted JavaScript build, malicious extension, infected device or screen/clipboard observer can steal a displayed phrase or an unlocked session. Vault encryption protects stored ciphertext; it does not protect secrets after the user unlocks a malicious application. JavaScript strings and WebCrypto keys cannot be guaranteed to be completely erased from memory. Dependency pinning, CSP and the implemented checks reduce specific risks; they do not replace independent review, controlled release provenance and recovery testing on every supported browser.

The [build manifest and endpoint](PROVENANCE.md) let an operator identify a release and compare its recorded file hashes. These are operator-supplied metadata, not an independent cryptographic proof that a host serves honest code. A compromised host can replace both code and metadata. Review independently obtained sources and artifacts; matching the endpoint alone does not establish the integrity of the browser or host.
